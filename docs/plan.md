# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- FastAPI와 React를 사용합니다. 실제 서비스 DB는 Supabase PostgreSQL, 초기 개발·자동 테스트 DB는 SQLite3로 구분합니다.
- React는 FastAPI API를 통해 데이터를 읽고 변경하며 서버에서 모든 권한을 검사합니다.
- 회원 인증, 데이터 접근, 마이그레이션 도구는 Phase 0에서 정하고 꼭 필요한 패키지만 추가합니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ app/
│  │  ├─ main.py       # FastAPI 시작점
│  │  ├─ core/         # 환경 설정, 인증과 공통 권한
│  │  ├─ db/           # DB 연결과 공통 저장 처리
│  │  ├─ accounts/     # 회원 API와 사용자 데이터
│  │  ├─ records/      # 공부·할 일·오류 API와 데이터
│  │  └─ community/    # 댓글·좋아요·신고 API와 데이터
│  ├─ migrations/      # 데이터베이스 구조 변경 이력
│  └─ tests/           # API·데이터·권한 자동 테스트
├─ frontend/
│  ├─ package.json
│  ├─ src/
│  │  ├─ api/          # FastAPI 요청
│  │  ├─ components/   # 공통 메뉴·폼·카드
│  │  ├─ pages/        # 사용자 화면
│  │  └─ styles/       # 공통 디자인
│  └─ public/          # 정적 파일
├─ database/
│  └─ buildlog.sqlite3 # 초기 개발용 데이터, Git 제외
└─ docs/               # 요구사항, 동작 설명서, 개발 문서
```

기존 `frontend/mvp.md`, `frontend/PRD.md`와 README는 보존합니다. 기존 문서 위치를 바꾸지 않습니다. 테스트마다 별도 SQLite3 DB를 사용해 개발 데이터를 오염시키지 않습니다.

Supabase Auth는 데이터베이스와 별개의 선택 사항입니다. 사용 여부는 미정이며 Phase 0에서 결정합니다. Phase 0 점검에서 React 실행 도구는 Vite·npm, 데이터 접근은 SQLAlchemy, 마이그레이션은 Alembic으로 선정했습니다. 설치·호환 실행 검증은 아직 하지 않았습니다. 아래 사용자 모델·인증 작업은 그 결정에 맞춰 구현합니다.

## 4. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | 실행 가능한 FastAPI·React 뼈대 | 화면과 API가 각각 실행되고 연결됨 |
| 2 | 사용자 모델과 데이터베이스 시작점 | 첫 마이그레이션과 사용자 모델 테스트 통과 |
| 3 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 4 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 5 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 6 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 7 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 8 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 9 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 10 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 11 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 12 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 13 | Supabase 연결과 PostgreSQL 검증 | 실제 서비스 DB에서 기능·제약 검증 통과 |
| 14 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

각 기능 단계에서는 FastAPI API·입력 스키마·서버 권한 검사·데이터 처리를 먼저 만들고 React 화면과 연결합니다. API 테스트와 React 화면 테스트를 함께 작성합니다. React는 DB에 직접 접근하지 않습니다. 읽기는 조회 요청으로, 데이터 변경은 상태 변경 요청으로 구분합니다. 인증 방식에 맞는 요청 보호와 오류 응답 규칙을 적용합니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. Python·FastAPI와 Node.js·React의 호환되는 안정 버전을 확인합니다. React 실행 도구와 패키지 관리자를 정합니다.
4. SQLite3가 Python 환경에서 사용 가능한지 확인합니다. Supabase는 PostgreSQL 기반임을 반영해 데이터 접근·구조 변경 도구를 정합니다.
   - Supabase Auth 사용 여부와 로그인 유지 방식을 먼저 결정합니다.
   - spec 6.1의 새 오류 미해결 기본값과 처음부터 해결 상태 저장 허용 설명을 확인합니다.
   - 기록·댓글 삭제 시 연결된 댓글·좋아요·신고 처리, 이메일·닉네임 대소문자, 검색·필터 동시 적용 규칙을 확인합니다.
   - 미정 사항은 하나씩 질문하고 답변 전에는 관련 동작을 임의로 구현하지 않습니다.
5. 화면 주소 `http://localhost:5173`, API 주소 `http://localhost:8000`을 기본 제안으로 정리합니다. 포트 사용 여부를 확인하고 초기 개발 DB 파일 위치, 테스트 DB 분리, 환경 변수 이름과 허용할 프론트 주소를 정리합니다.
   - 변수 예시: 서버의 `DATABASE_URL`, 테스트용 `TEST_DATABASE_URL`, 허용 프론트 주소 설정, React의 `VITE_API_BASE_URL`(Vite 선택 시).
   - 서버 인증용 비밀값과 Supabase 연결 정보는 인증 방식 결정 후 확정합니다. 실제 비밀값은 문서에 기록하지 않습니다.
6. 테스트 명령과 서버 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python·Node.js·패키지 관리자 실행 여부와 SQLite3 버전을 읽기 전용 명령으로 확인합니다. 호환성은 실제 개발 시 공식 문서에서 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

React 화면과 FastAPI 서버를 각각 실행하고 화면에서 API 응답을 확인합니다.

#### 작업

1. `backend/.venv`에 가상환경을 만들고 FastAPI 실행에 필요한 패키지와 버전을 기록합니다.
2. `backend/app/main.py`와 환경 설정·DB 연결 준비 코드를 만듭니다.
3. Phase 0에서 정한 도구로 `frontend`에 React 프로젝트를 만듭니다. 기존 문서를 덮어쓰지 않습니다.
4. React 기본 화면과 공통 API 요청 함수를 만듭니다.
5. FastAPI 상태 확인 API를 연결하고 React에서 응답을 확인합니다.
6. 서로 다른 개발 서버 간 통신을 위해 허용할 프론트 주소를 서버에 설정합니다(CORS 설정).
7. 비밀값은 서버 환경 변수로 읽고 `.env.example`에는 이름과 비밀이 아닌 안내만 기록합니다. 프론트 환경 변수에는 API 주소처럼 공개 가능한 값만 넣습니다.
8. SQLite3 경로를 준비하고 `.gitignore`에 DB 파일·설치 폴더·생성 결과 제외를 보완합니다.
9. 이 단계에서는 DB 구조 생성과 사용자 데이터 입력을 하지 않습니다.

#### 예상 변경 파일

- `backend/requirements.txt`, `backend/app/main.py`, `backend/app/core/`, `backend/app/db/`
- `frontend/package.json`, 선택한 도구의 설정·잠금 파일, `frontend/src/`, `frontend/public/`
- 서버·프론트용 `.env.example`, `.gitignore`
- 기본 API 테스트와 React 연결 확인용 테스트

#### 확인 방법과 완료 조건

- API 상태 확인 자동 테스트와 React 기본 화면 테스트가 통과합니다.
- 실제 브라우저에서 React 화면·스타일·API 연결을 확인합니다.
- 허용한 프론트 주소에서만 브라우저 연동이 가능하고 비밀값이 화면·프론트 산출물에 없습니다.
- 아직 데이터베이스 구조 변경을 실행하지 않았습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. `backend/app/accounts` 모듈을 만듭니다.
2. 선택한 인증 방식에 맞춰 사용자 모델을 만듭니다. 자체 인증이면 해시 비밀번호를 저장하고, Supabase Auth를 쓰면 인증 사용자 ID와 프로필을 연결하며 비밀번호를 중복 저장하지 않습니다.
3. 이메일은 필수이며 중복되지 않게 합니다.
4. 닉네임은 필수이며 중복되지 않게 합니다.
5. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
6. 자체 인증이면 검증된 비밀번호 해시 도구를 사용하고, Supabase Auth이면 비밀번호 처리를 인증 서비스에 맡깁니다. SQLite3 테스트에서도 선택한 방식의 인증 연동과 권한을 검증할 방법을 준비합니다.
7. 이메일로 로그인할 수 있도록 인증 처리를 연결합니다.
8. 사용자 모델과 DB 연결을 연결한 뒤 선택한 도구로 첫 마이그레이션을 만듭니다.
9. 빈 SQLite 데이터베이스에 마이그레이션을 적용합니다.
10. 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/accounts/models.py`
- `backend/app/accounts/services.py`
- `backend/app/accounts/schemas.py`
- `backend/tests/accounts/`
- `backend/app/core/config.py`
- `backend/migrations/`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 모델 테스트가 모두 통과해야 합니다.
- 사용자 모델을 다시 바꾸기 위해 데이터베이스를 지워야 하는 문제가 없어야 합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API와 React 입력 화면을 만듭니다.
2. 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
4. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 React 화면을 만들고 이메일로 로그인하게 합니다.
6. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
7. 로그인 성공 시 내 기록 홈 화면으로 이동합니다.
8. 로그인하지 않은 사용자가 기록 화면에 접근하지 못하게 합니다.
9. 계정 설정에서 닉네임을 변경하게 합니다.
10. 공개 기록과 댓글에서 사용자 객체의 현재 닉네임을 읽도록 준비합니다.

#### 예상 변경 파일

- `backend/app/accounts/schemas.py`
- `backend/app/accounts/routes.py`
- `backend/app/accounts/router.py`
- `backend/tests/accounts/`
- `backend/app/main.py`
- `frontend/src/pages/accounts/Signup.jsx`
- `frontend/src/pages/accounts/Login.jsx`
- `frontend/src/pages/accounts/Settings.jsx`
- `frontend/src/pages/Home.jsx`

### Phase 13. Supabase 연결과 PostgreSQL 검증

#### 목표

SQLite3에서 만든 기능을 실제 서비스 DB인 Supabase PostgreSQL에서도 확인합니다. 외부 인터넷 배포는 이 단계의 목표가 아닙니다.

#### 작업

1. 사용자가 준비한 개발용 Supabase 프로젝트와 연결 방식을 확인합니다. 실제 운영 데이터가 있는 프로젝트는 테스트에 사용하지 않습니다.
2. 연결 정보는 서버의 환경 설정에만 넣습니다. 비밀번호나 서버 전용 키를 채팅·문서·React 코드에 기록하지 않습니다.
3. PostgreSQL 드라이버·연결 설정을 적용하고 같은 구조 변경 이력을 빈 개발 DB에 적용합니다.
4. 사용자·기록·댓글·좋아요·신고를 저장하고 조회·수정·삭제합니다.
5. SQLite3와 차이가 날 수 있는 길이 제한, 검색 대소문자·한글, 중복과 빈 값, 날짜·시간, 관계와 삭제 규칙, 실패 시 전체 취소 처리를 검증합니다.
6. 선택한 인증 방식으로 실제 가입·로그인·운영자 권한을 확인합니다. 인증 서비스를 테스트 대역으로 확인한 부분이 있다면 실제 연동도 확인합니다.
7. SQLite3 자동 테스트를 유지하고 PostgreSQL 연동 테스트는 별도 명령·환경으로 분리합니다. 운영 DB를 자동 초기화하거나 테스트 데이터를 섞지 않습니다.
8. 로컬 SQLite3 데이터를 Supabase로 옮겨야 하는지는 별도 결정합니다. 파일을 그대로 업로드하지 않습니다.

#### 예상 변경 파일

- `backend/app/core/`, `backend/app/db/`, `backend/requirements.txt`, `backend/migrations/`
- `backend/tests/integration/`, 서버 `.env.example`, `docs/setup.md`

#### 확인 방법과 완료 조건

- Supabase PostgreSQL에 구조가 생성되고 모든 기능의 데이터 흐름이 동작합니다.
- 비공개 권한·중복 좋아요·중복 신고·작성자 권한과 운영자 전용 조회가 실제 연동에서도 유지됩니다.
- SQLite3와 PostgreSQL에서 요구사항 결과가 같고 차이로 인한 실패를 수정했습니다.
- 프론트에 DB 비밀번호·서버 비밀키가 없고 테스트가 운영 데이터를 변경하지 않습니다.
